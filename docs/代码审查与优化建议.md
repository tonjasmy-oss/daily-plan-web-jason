# 工程管理系统 · 前端代码审查与优化建议

> 审查范围：`assets/` 下全部 JS（约 1.25 万行）+ 项目结构（HTML 按序 `<script>` 引入、Python 后端 `server/app.py`、无打包构建）。
> 审查日期：2026-09-28 ｜ 视角：全栈开发 / 可维护性 / 数据安全

---

## 一、总体评价

这是一套**功能完整、业务闭环清晰**的工程管理系统（日报、日/周计划、审批、物资申购、角色权限、导出）。代码可读性整体不错，注释充分，且有几处亮点：

- ✅ `esc()` 全局 HTML 转义，从源头防 XSS；
- ✅ 权限采用 `all / list / legacy` 三态模型，兼顾管理员放行与老数据兼容，设计合理；
- ✅ 乐观更新 + PUT 防抖合并（400ms）+ 顺序 Promise 链，写体验好；
- ✅ `bootstrapDB()` 单例加载、`401` 统一跳登录、`validateName` 等校验集中。

但项目是典型的**"无构建的原生 JS 单体"**，随功能膨胀已出现明显的重复、脆弱点与数据安全风险，建议按优先级逐步重构。

## 二、高优先级（数据安全 / 健壮性）

### 🔴 P0-1 写操作无重试、无离线兜底 → 现场数据可能静默丢失
- 位置：`common.js` `_syncNow()`（L287-308）、`_syncRecord()`（L311-325）
- 问题：所有写请求走单一 `_chain` 串行队列，且 `.catch` 仅 `console.error + toast` 后 **resolve**，调用方拿不到失败信号。一旦请求失败（网络抖动、服务重启），内存缓存里已乐观更新的数据**从未落任何本地存储**，刷新页面即丢失。
- 风险：工程现场填报的日计划/申购可能因一次网络失败而"消失"，且用户无感知。
- 建议：
  1. 引入**本地 Outbox**：待确认写请求先入 `localStorage` 队列，服务端 ACK 后再出队；
  2. `_syncNow` 失败应**重试（指数退避，最多 3 次）**，仍失败则在 UI 显式标记"未同步"角标，而非静默 resolve；
  3. 单一 `_chain` 改为**按实体分链**（或并发 + 失败隔离），避免一个慢请求阻塞全部写入。

### 🔴 P0-2 新建记录不回写服务端 `_id`，存在 id 不一致风险
- 位置：`common.js` 各 `createProject / createMember / createTask / createDailyPlan / …`（L377、L420、L471、L813 等）
- 对比：`createWorkType()`（L229-233）**会**用 `body.record._id` 回写本地记录，而上面这些 `create*` **不会**读取响应、直接用客户端 `uuid()` 当 `_id`。
- 风险：需核对后端 `server/app.py` 是否在 POST 时**自生成 id**（如 rowid/雪花）。若自生成，则本地 `_id` 与库内不一致 → 后续 `updateX/deleteX` 打向 `/api/projects/<clientUuid>` 会 404 静默失败，更新永远写不进去。
- 建议：统一封装 `create` 流程，POST 成功后将 `res.record._id / created_at` 回写本地缓存（与 `createWorkType` 对齐），消除差异。

## 三、中优先级（可维护性 / 重复代码）

### 🟠 P1-1 `common.js` 超大单体 + 全局命名空间
- 位置：`common.js`（1918 行，60+ 全局 `var/function`，全部挂在 `window`）
- 问题：无模块、无命名空间、无构建。任意文件新增同名函数即冲突；无法单测、无法 tree-shake。
- 建议（渐进式，不必一次大改）：
  - 第一步：把函数收进命名空间对象，如 `window.ENG = { db, api, auth, ui, perm, fmt }`，减少全局污染；
  - 第二步：按域拆文件（`db.js / api.js / auth.js / modal.js / perm.js / entities.js`），用 `<script type="module">` 引入（项目已用 http 服务，模块可用）。

### 🟠 P1-2 38 个 CRUD 函数样板几乎一致
- 位置：`common.js` 共 12 个 `create*`、14 个 `update*`、12 个 `delete*`
- 每个实体都是同一形状：
  - `create`：补默认值 → push 缓存 → `_syncNow('POST')` → return
  - `update`：`_findIdx` → `Object.assign` 合并 + `updated_at` → `_syncRecord('PUT')`
  - `delete`：filter 剔除 → `_syncNow('DELETE')`
- 建议：抽通用工厂
  ```js
  function makeCrud(cfg) { /* cfg: {arr, endpoint, defaults, idFn} */
    return {
      create(d){ … }, update(id,p){ … }, remove(id){ … },
      list(){ return DB[cfg.arr]; }, get(id){ return _findById(DB[cfg.arr], id); }
    };
  }
  const projects = makeCrud({ arr:'projects', endpoint:'/api/projects', defaults:{status:'planning'} });
  ```
  预计可裁剪 ~400 行，且 `_id` 回写（P0-2）、`updated_at` 戳、失败处理都只在一处维护。

### 🟠 P1-3 模态框系统脆弱 + "清场"脚枪
- 位置：`common.js` `confirmDialog / promptDialog / multiSelectDialog / confirmDialogEx`（L1707、1739、1774、1844）
- 问题：
  1. 四个实现各自重复 overlay 创建、关闭、ESC、背景点击逻辑；
  2. **致命脚枪**：每个 dialog 打开时都执行 `document.querySelectorAll('.modal-overlay').forEach(el=>el.remove())`，会**清掉页面上所有** `.modal-overlay`。`plan-shared.js` L505-507 注释已承认 `multiSelectDialog` 会摧毁所在详情弹层，于是 `peoplePicker` 被迫内联规避 —— 这是用 workaround 补窟窿。
- 建议：统一 `openModal({html, onConfirm, onCancel, closeOnBackdrop})`，返回句柄；详情弹层改用独立类名（如 `.pb-overlay`，已部分如此），dialog 只关自己、不误伤别人；删掉内联规避代码。

### 🟠 P1-4 角色解析逻辑重复
- 位置：`resolveRoleModules()`（L768-784）与 `resolveRolePerms()`（L1117-1131）
- 问题：两段都重复"按 `key/_id` 找角色 + admin 放行 + legacy 回落"，约 20 行一致。
- 建议：抽 `findRoleRecord(user)` 返回命中角色，两函数复用。

### 🟠 P1-5 权限/模块复选框网格重复
- 位置：`roles.js` `paintPermGrid`(L73) 与 `paintModulesGrid`(L151)
- 问题：两函数约 90% 相同（复选框网格 + 全选 + cell 样式同步），已出现样式细节分化风险。
- 建议：抽通用 `paintCheckGrid(items, checkedIds, opts)` + `bindCheckGrid(scope, cellSel, onChange)` + `_syncCell/_syncToggleAll`。

## 五、性能（当前数据量下影响小，规模增长后需注意）

- `roleLabel/roleIcon`（`common.js` L81-96）每次调用都 `loadRoles().filter().find`，在渲染循环里（每个成员 chip 调一次）为 O(成员×角色数)。建议在 `DB.roles` 变更时构建一次 `Map<key, role>`，或加 memo。
- `syncProjectProgress`（`common.js` L530）每次任务增改删都对全部 `tasks` 过滤求平均（O(n)），小数据无感，大数据可增量维护。

## 七、建议实施路线

1. **P0（数据安全，必修）**：离线写队列 + 失败重试 + `create` 统一回写 `_id`。
2. **P1（可维护，强烈建议）**：CRUD 工厂、模态框统一、角色解析抽函数、ICONS 统一。
3. **P2（一致性）**：状态/常量/图标/权限网格去重、初始化模式统一。
4. **P3（性能/测试）**：`roleLabel` 缓存、`syncProjectProgress` 优化、补单测。

> 注：以上重构均可在**不改动后端、不改变现有页面行为**的前提下渐进完成，建议优先做 P0-1/P0-2 与 P1-2（CRUD 工厂），投入小、收益大、风险低。

## 八、实施记录（2026-09-28）

### ✅ P0-2 新建记录统一回写服务端 `_id` —— 已完成
- 在 `common.js` 新增通用 `makeCrud(cfg)` 工厂；其 `create()` 在 POST 响应返回后，用 `res.record._id` / `res.record.created_at` **回写本地缓存记录**（与 `createWorkType` 行为对齐）。
- 后端核实：`server/app.py` 通用接口为 `data.get('_id') or gen_id(...)`（L1209/L1255/L1276），**当前优先复用客户端 `_id`**，故回写为"防御 + 向前兼容"——即使后端未来改为自生成 id，前端也能正确对齐，不会 404。
- 覆盖实体：项目 / 人员 / 任务 / 日计划 / 周计划 / 周报 / 申购 / 审批 / 申购批次 / 部门 / 角色（共 11 个），外加原本已回写的工种。

### ✅ P1-2 38 个 CRUD 函数抽离为工厂 —— 已完成
- 11 个实体的 `create/update/delete/load/get` 收进 `makeCrud` 工厂，页面侧仅保留**薄包装**（同名全局函数，签名不变，调用方零改动）。
- 特殊逻辑用工厂钩子保留，行为与原实现逐一对齐：
  - 任务：`beforeCreate` 写入首条 history（含 `reporterId`）；`beforeUpdate` 在状态变更时追加 history 并消费临时字段 `_changedBy`；`afterCreate/afterUpdate/afterDelete` 同步项目进度；
  - 项目：`beforeDelete` 级联剔除其任务（服务端已联删，不逐条同步）；
  - 人员：`beforeDelete` 解除其在项目/任务里的关联并逐条 PUT；
  - 11 个实体按原样保留 `push` / `unshift`（计划/申购类置顶）与各自 `_id` 前缀（`dp_`/`wp_`/`wr_`/`pu_`/`ap_`/`pg_`/`d_`/`r_`）。
- 验证：用 Node 沙箱桩加载 `common.js` 跑 33 项断言（建/改/删、id 前缀、unshift 置顶、回写、级联、解绑、状态 history、异步 `createWorkType` 未受影响），**全部通过**；`node --check` 语法校验通过。

### 关于行数
- 文件由 1918 → 1890 行（净减约 28 行），**并未如预估裁剪 ~400 行**——因为 11 套样板改写为「工厂(~90 行) + 显式配置(~150 行) + 薄包装(~55 行)」。
- 真正的收益是**消除 ~270 行重复逻辑、统一在单点维护**（增删改流程、`_id` 回写、`updated_at`、失败处理、级联规则），并顺带修了原实现里部分 `create*` 缺 `rec._id = rec._id || uuid()` 兜底行的不一致。行数不是本次目标。

### ✅ P0-1 写失败重试 + 离线 Outbox + 按实体分链 —— 已完成
- 在 `common.js` 同步层重写（原单一 `_chain` 串行队列 + 失败静默 `resolve` 全部移除），新增：
  - **Outbox 持久化**：所有写请求（POST/PUT/DELETE）先落本地 `localStorage`（`eng_ms_outbox_v1`）再发送；刷新 / 崩溃 / 断网都不会静默丢写。
  - **指数退避重试**：`_attempt()` 首次失败按 `1s→2s→4s…` 退避（封顶 30s）递归重试，超出 `MAX_ATTEMPTS`(6) 转 `failed` 等待重放；每个 Outbox item 用稳定 `deferred`，重试多次也只 resolve/reject 一次（最终态）。
  - **按实体分链**：`_chains[entity]` 取代单一 `_chain`（如 `/api/projects`→`projects`），同实体保序、不同实体并行，单一慢请求不再阻塞全部写入。
  - **重放时机**：`window 'online'` 事件 + `bootstrapDB()` 成功/失败分支均触发 `_replayOutbox()`（失败分支让 Outbox 自动退避重试自愈）；`auth_error`(401) 项跳过重放（等重新登录）。
  - 401 行为保留：跳 `login.html` 并停止该请求重试；其余失败不再 `toast` 静默吞掉（改为 console.error + 进 Outbox 自愈）。
- **边界（未改动）**：`createWorkType / updateWorkType / deleteWorkType` 走自有 `await fetch` + 乐观回滚 + throw，不经过 `_syncNow`，既有回滚语义保持不变。
- 验证：Node 沙箱桩加载 `common.js` 跑 **14 项断言**——失败重试 + Outbox 落盘 + 重试后清空 + `_id` 回写、按实体分链不互相阻塞、超限转 `failed`、网络恢复重放、401 跳登录并停止重试——**全部通过**；`node --check` 语法校验通过。
- 行数：文件 1918 → 1985 行（净增约 67 行，为 Outbox/重试/分链逻辑）。
